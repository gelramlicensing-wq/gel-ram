# Native silicon evidence — 2026-09-04

This file records the measurement runs made on 2026-09-04 for this tree. It
is evidence for the binary memory engine on one machine, not a universal
performance claim. It supersedes the sequential and random-fetch rows of
`docs/SILICON-2026-09-03.md` and adds the build-target and thread axes that
record lacked.

- machine: AMD Ryzen AI 9 HX 370, 12 cores / 24 threads; two L3 domains
  reported by the OS: 16 MiB (cpus 0-3,12-15, Zen5) and 8 MiB
  (cpus 4-11,16-23, Zen5c); Linux 6.17; THP policy `always [madvise] never`;
  cpufreq governor `powersave`, EPP `balance_performance`
- compiler: rustc 1.85.0 commit `4d91de4e48198da2e33413efdcd9cd2cc0c46688`,
  host `x86_64-unknown-linux-gnu`, LLVM 19.1.7
- source identity: tree content SHA256, computed as `git ls-files | grep -v SILICON-2026-09-04 | LC_ALL=C sort | xargs sha256sum | sha256sum` (every tracked file except this
  record):
  `08d98327c312d022e9bee9debeda561b7de295c3c780a2a368cc77bb89ad21f9`. The release archive SHA256 is published in the
  sidecar file distributed next to the archive.
- load discipline: `load1` was read before and after every run and is
  quoted per table; no `rustc`/`cargo` process was running during the bench

## Build variants and disassembly

Five release builds of the same source, differing only in `RUSTFLAGS`
(`CARGO_TARGET_DIR` separated). Results (bank CRC, Top-1 index and score,
flip survival, null query, progressive counters) were identical for all
three; only time differs.

| variant | rustflags | `backend=` line | `popcnt` instructions in `gel-bench` | `vpopcntq` (AVX-512) instructions |
|---|---|---|---|---|
| baseline | `-C target-cpu=x86-64` | `count_ones(popcnt=false,avx2=false)` | 0 | 0 |
| popcnt | `-C target-feature=+popcnt` | `count_ones(popcnt=true,avx2=false)` | 41 | 0 |
| native | `-C target-cpu=native` | `count_ones(popcnt=true,avx2=true)` | 16 | 20 |
| x86-64-v3 | `-C target-cpu=x86-64-v3` | `count_ones(popcnt=true,avx2=true)` | 24 | 0 |
| default | `-C target-cpu=native -C target-feature=-avx512f` | `count_ones(popcnt=true,avx2=true)` | 24 | 0 |

Instruction counts are `objdump -d` line counts. On Rust 1.85 the AVX-512
target features are not observable through `cfg`, so the `backend=` line
cannot show `vpopcntq`; the disassembly count is the evidence. The default
build of this tree is the last row: native with AVX-512 switched off (`.cargo/config.toml`); its `gel-physics` binary contains no `zmm` instruction.

Observations, stated as measured:

- The baseline Zen5 row (169.8 M ORB/s) reproduces the unpinned
  2026-09-03 record (168.8 M ORB/s) within 1 %, which places that record on
  the Zen5 domain.
- The baseline build emits no POPCNT instruction; its scan is compute-bound.
  The popcnt build is 1.67x faster on Zen5 and the native build 2.09x. On
  Zen5c the native build is 3.2x faster than baseline and within 4 % of the
  Zen5 native row, so with POPCNT/AVX-512 the single-thread scan is no
  longer separated by core type.
- bank CRC64-ECMA `72442fd264cb251f`, null Top-1 index 155,424 score
  587/1024, flip survival 1/8/32/64/128/256/384 all true, progressive Top-8
  PASS with 0/0 rejects, in every run.
- The default build (AVX-512 off) rows were measured at `2026-09-04T18:32:16Z` with
  `load1` 2.4-2.6 and a memory-bound control bench (default `gel-bench 1310720 3 1`
  on cpu 0) of 354 / 310 M ORB/s around the Zen5 row and 350 / 345 M around the
  Zen5c row. On the Zen5 core the default build equals the AVX-512 build
  (355.8 M against 355.6 M ORB/s): the scan is memory-bound there and `vpopcntq`
  adds nothing. On the Zen5c core AVX-512 is faster (342.0 M against 266.8 M
  ORB/s, 1.28x); the default trades that for probe correctness (see Memory
  physics).

### Why AVX-512 is off in the default build

Measured on the Zen5 core with the same v3 probe source, control bench passing
before and after each run:

| build | 48 KiB (L1) GiB/s | 256 MiB (RAM) GiB/s | random fetch 128 B |
|---|---|---|---|
| native with AVX-512, one accumulator chain (v3 first cut) | 43.3 | 6.9 | 39.6 ns |
| native with AVX-512, eight accumulator chains | 32.0 | 3.9 | 10.1 ns |
| native without AVX-512 (default), eight chains | 305.0 | 40.0 | 12.1 ns |
| x86-64-v3 (AVX2), eight chains | 230.7 | 42.6 | 12.7 ns |
| x86-64 baseline (SSE2), v2 probe | 104.7 | 39.8 | 25.1 ns |

An L1-resident row cannot be slowed by other cores, and the pointer-chase rows
of the AVX-512 runs matched the clean baseline rows, so the gap is code
generation: with AVX-512 enabled the reduction compiles to a `vpaddq zmm` loop
(`objdump`: 152 `zmm` loads, 83 `vpaddq zmm`), which on this mobile Zen5 (512-bit
operations executed as two 256-bit halves) runs at 32-43 GiB/s from L1 and
cannot keep the memory system busy, while the AVX2 (`ymm`) loop reaches
305 GiB/s from L1 and 40 GiB/s from RAM. Buffer alignment was tested as the
cause first and refuted: 64-byte-aligned buffers left the AVX-512 row at
43.3 GiB/s. The default build therefore disables `avx512f`; the full scan loses
nothing on the Zen5 core and 28 % on the Zen5c core, and every physics row
becomes a memory number. Compare rows only within one probe tag and one build.
