# Native silicon evidence — 2026-09-03

## Addendum 2026-09-04

The measurements below are reproduced unchanged. Re-measurement on the same
machine on 2026-09-04 established the following limits of this record:

- The run was unpinned. The machine has two L3 domains: 16 MiB (Zen5 cores)
  and 8 MiB (Zen5c cores).
- Full scan: on 2026-09-04 the same bench command measured about 164 M ORB/s
  unpinned, about 154 M ORB/s pinned to one Zen5 core (`taskset -c 0`) and
  about 108 M ORB/s pinned to one Zen5c core (`taskset -c 4`), both under
  rising load. The record is consistent with the 16 MiB domain.
- Pointer chase: the rows from 48 KiB to 24 MiB are not reproducible without
  pinning. Measured on 2026-09-04: 48 KiB 2.25 ns unpinned vs 1.01 ns pinned
  to a Zen5 core; 12 MiB 16.4 ns pinned to a Zen5 core vs 70.5 ns pinned to a
  Zen5c core. Pin to one domain and report it; see `docs/PERFORMANCE.md`.
- Sequential: the rows were produced by the F0 v1 probe
  (`GEL_PHYSICS_F0_V1`), whose per-element barrier capped its 48 KiB
  (L1-resident) row near 40 GiB/s, unpinned and pinned to a Zen5 core. The
  64/256 MiB rows below cannot be separated from that cap.
- Random fetch: the rows were produced by the v1 probe and are reported
  as-is. The v3 probe moved the barrier from each element to each fetch, so
  v1 and v3 random-fetch rows are not comparable.
- The full-scan record was printed by `GEL_BENCH_V2`. Its
  `backend=portable-popcount` corresponds to `count_ones(popcnt=false,avx2=false)`
  in `GEL_BENCH_V3`: default x86_64 target, no POPCNT instruction emitted.
- The source SHA256 of the tree used for this run was not recorded.
- `docs/SILICON-2026-09-04.md` supersedes the sequential and random-fetch
  rows.

This file records one local diagnostic run. It is evidence for the binary
memory engine on one machine, not a semantic AI benchmark or a universal
performance claim.

## Memory physics

Command: `cargo run --locked --offline -p xtask -- physics 3`.

Pointer-chase p50 ns/step for 48 KiB, 1 MiB, 6 MiB, 12 MiB, 24 MiB,
64 MiB and 256 MiB was respectively 2.261, 4.935, 10.474, 42.805,
91.029, 103.879 and 127.142 ns.

Sequential p50 bandwidth for 64 MiB and 256 MiB was 28.013 and
30.840 GiB/s. Random fetch p50 from a 64 MiB working set was 15.677 ns
for 32 B, 31.476 ns for 64 B and 50.951 ns for 128 B.

The Linux THP policy was `always [madvise] never`. This reports policy only;
it does not prove that these allocations used transparent huge pages.
